# 清理任务与 LLM 分析日志设计

日期：2026-09-08  
状态：需求已通过多轮讨论确认，代码已实现；验证结果见第 12 节。

## 1. 用途与已确认决策

为用户反馈问题提供可直接打开阅读的文本日志，帮助开发者定位扫描及 LLM 分析问题。本文的可审计性指需求、实现位置与验收条件可以相互核对；日志本身不承担合规审计、计费凭证或严格身份核验职责。

| 项目 | 已确认行为 |
| --- | --- |
| 创建时机 | CleaningRecord 创建成功后立即创建日志，覆盖扫描及分析阶段 |
| 路径 | 当前运行 exe 所在目录下的 logs 目录 |
| 文件名 | 根据 CleaningRecord.StartTime 生成，采用本地时间，精确到毫秒 |
| 阅读方式 | 普通文本，用户手动打开；无前端入口 |
| token 更新 | 每轮 LLM 请求结束后立即记录本轮和累计用量 |
| 开始上下文 | 时间、路径、分析配置和扫描摘要 |
| 工具 | 执行前记录调用 ID、工具名、完整参数；不记录响应 |
| 排除正文 | 不记录 system/user prompt 和 LLM 普通回复正文 |
| 日志故障 | 创建或写入失败仍继续分析 |
| 记录删除 | 先删日志，再通过数据库事务删记录 |
| 批量删除故障 | 某条日志删除失败则跳过对应记录，继续处理其他记录 |
| 文件不存在 | 视为文件清理成功，继续删除记录 |
| 简化关联 | 不新增 LogFileName 字段、不要求日志头记录记录 ID、不处理时区变化 |

## 2. 当前代码与接入依据

- `backend/service/cleaner/cleaner.go`：StartCleaning 在扫描前创建 CleaningRecord；activeTask 持有任务状态；StopCleaning 只请求取消。
- `backend/service/cleaner/task.go`：run 串联扫描、分析、结果落库；finish 收敛成功、失败、取消状态。
- `backend/service/analyzer/analyzer.go`：Analyze 加载配置并创建 Agent；当前签名没有任务日志参数。
- `backend/service/analyzer/agnet.go`：以 stream=false 调用 Chat Completions；返回后更新 usedTokens 和 totalTokens；现有 myLog 只写标准输出。
- `backend/service/analyzer/tools.go`：统一工具入口为 manager.Invoke；resetAnalyzeContext 中有状态变化日志。
- `backend/service/cleaninghistory/cleaninghistory.go`：启动时修复中断任务，再按保留数量删除历史。
- `backend/data/models/cleaningrecord/cleaningrecord.go`：DeleteOldCleaningRecords 当前在事务中选 ID 并删除记录，尚无文件处理。
- `backend/service/service.go`：统一构造、启动并发布服务实例。

当前检索到的生产记录删除入口为上述启动清理。删除候选垃圾文件不等于删除 CleaningRecord，不触发日志清理。已有上下文压缩 OpenSpec 文档与 tools.go 的部分状态描述不同，本功能按当前实现记录实际变化，不顺带调整压缩策略。

## 3. 文件规则

路径计算统一放在日志服务中：

```text
filepath.Join(filepath.Dir(os.Executable()), "logs", filename)
filename = StartTime.Local().Format("2006-01-02_15-04-05.000") + ".log"
示例：logs/2026-09-08_14-30-05.123.log
```

StartTime 是文件名唯一时间来源，创建和删除共用同一格式化函数，不能用打开文件时的 time.Now() 替代。事件时间使用事件实际发生的本地时间，格式同样精确到毫秒。

目录按需创建。使用 UTF-8 文本，以追加方式打开文件；不截断已有文件。每条事件即时写入文件，不等待任务结束或定时批量刷新；无需逐条 fsync，进程崩溃或断电时不保证最后事件持久化。

不增加数据库字段、ID 后缀、文件索引、时区元数据或孤儿文件扫描。用户移动 exe、修改时区或手动移动日志后，按既定路径找不到就算了。极端情况下相同毫秒时间会映射到同一文件，采用追加行为；接受这一简化，不构建重名解决机制。开发运行也以实际进程可执行文件目录为准。

## 4. 职责与接口设计

### 4.1 tasklog 服务

新增 `backend/service/tasklog/tasklog.go`，公开 Service、任务级 Session 及外部使用的方法。路径、格式化、文件写入等内部逻辑分放同目录私有文件。服务由根 service 管理器集中构造和持有，并增加 GetTaskLogService；遵循现有构造、发布及 getter 规则，不建立全局日志单例。

建议公开契约（名称为实现建议，可在不改变语义的前提下调整）：

| 契约 | 责任 |
| --- | --- |
| NewService | 仅由根管理器装配，不因日志目录不可写阻断应用启动 |
| Service.Open(startTime, path) → Session | 计算路径、打开文件、记录任务开始；失败报告应用日志并返回可用的空操作 Session |
| Service.Remove(startTime) → error | 删除唯一目标文件；不存在返回成功；其他错误交由历史服务逐条处理 |
| Session 的事件方法 | 记录扫描、分析、轮次、工具请求、状态变化及最终状态；写入错误不返回为业务失败 |
| Session.Finish(state, errorSummary) | 写结束事件并关闭文件；幂等；使用已记录的累计用量 |

Session 保存文件句柄、累计已知 token、统计是否完整、是否已结束/写入失败等状态。采用小范围互斥锁保护一次完整事件写入与关闭，避免多行参数和关闭交叉；不为此引入异步队列或后台 goroutine。累计统计由 analyzer 提供，Session 用于保留结束时所需快照，不参与 Agent 预算判断。

创建失败报告一次；写入失败后报告一次、关闭句柄并停用该 Session，避免每个事件重复刷错误。关闭失败也报告到现有应用日志，不能改变任务状态。空操作 Session 支持所有调用，调用方无需不断判断 nil。

### 4.2 cleaner

StartCleaning 在记录创建成功后打开 Session，保存到 activeTask；数据库创建失败不创建日志。日志写入不能回滚已成功创建的记录，也不能阻止启动任务。

扫描成功后记录目录大小与条目数。调用 Analyze 时显式传入 Session，不通过 context 隐式传递。StopCleaning 仍只请求取消；由工作流程收尾关闭日志，避免请求尚在返回时文件被提前关闭。

所有正常返回路径最终关闭 Session：成功、扫描失败、配置加载失败、LLM 失败、取消和结果落库失败都需要覆盖。finish 写最终状态并关闭，再释放 active 状态、通知完成；run 同时安排幂等关闭兜底以防已有提前返回分支遗漏。兜底不能伪造成功状态。进程被强制终止不保证存在结束行。

任务结束状态以 cleaner 的实际结果为准：LLM 返回成功但结果落库失败时写“失败”，仍保留已获得的 token 用量。状态落库本身失败时，日志说明“状态保存失败”，不宣称数据库一定已更新。

### 4.3 analyzer

扩展 cleaner.Analyzer 接口和 analyzer.Service.Analyze，传入同一个任务 Session，并在 newAgent 返回后绑定到 Agent。Agent 内部通过窄日志接口便于测试；生产使用同一 Session。analyzer 不负责决定文件名或关闭文件。analyzer/config 读取失败由 cleaner 统一记录结束。

Agent.run 中替换本次任务相关的 myLog；tools.go 中现有状态日志也改写到 Session，避免任务日志分散。TestConnection 无 CleaningRecord，不创建此类日志。

### 4.4 服务装配

根管理器先构造 tasklog，再注入 cleaner 和 cleaninghistory；analyzer 经每次 Analyze 得到任务 Session。CleanupOnStartup 仍在发布服务之前执行。路径解析/日志删除故障不能作为整个应用初始化失败的原因；设置读取、候选查询或数据库删除失败沿用现有错误返回策略。

## 5. 事件格式与内容

```text
2026-09-08 14:30:05.123 [任务开始] 扫描路径=D:\Downloads
2026-09-08 14:30:08.010 [扫描完成] 占用=25.60 GiB 字节数=27487790694 条目数=12345
2026-09-08 14:30:08.012 [分析开始] 模型=example-model 语言=zh-CN Token预算=100000 自动压缩=开启
2026-09-08 14:30:11.012 [第1轮完成] 耗时=3.000s 输入Token=1200 输出Token=150 本轮Token=1350 累计已知Token=1350
2026-09-08 14:30:11.013 [工具请求] 轮次=1 调用ID=call_example 工具=analyze_directory
    参数：
    { ...完整参数... }
2026-09-08 14:30:20.000 [上下文压缩] 状态=low→medium 当前上下文Token=0 累计已知Token=5600
2026-09-08 14:30:30.000 [任务结束] 状态=成功 累计已知Token=8600 用量统计=完整 总耗时=24.877s
```

以上数据仅用于展示格式，不是实际运行输出。

| 事件 | 写入时机和字段 |
| --- | --- |
| 任务开始 | 记录创建后；StartTime、扫描路径；不要求记录 ID |
| 扫描完成 | 得到有效 tree 后；占用字节数、可读大小、条目数 |
| 分析开始 | 加载配置后、第一次请求前；模型、语言、token 预算、自动压缩开关 |
| 每轮完成/失败 | 一次 Chat.Completions.New 返回时；轮次、耗时、可用 usage、累计值、必要的错误摘要 |
| 工具请求 | 每个 manager.Invoke 前；轮次、调用 ID、名称、完整参数 |
| 上下文变化 | 实际发生压缩或状态切换时；变化前后状态、重置后的上下文用量、累计值 |
| 任务结束 | cleaner 收尾时；成功/失败/取消、总耗时、累计已知 token、完整性和错误摘要 |

参数为合法 JSON 时缩进展示；非法 JSON 保留原始文本并缩进，记录后仍走原有工具错误处理。每个多行事件整体写入，嵌入的换行不成为伪造的顶层日志行。参数不截断，包含 compress_context 的 summary；它属于已确认要保留的工具请求，不额外输出据此构造的 user prompt。

不记录工具返回值、工具返回的错误字符串、LLM 普通回复、完整 prompt、消息数组、HTTP 请求/响应体、API Key 或整个 config/extraBody。工具业务错误仍按原逻辑返回模型，不额外作为响应写入日志。

当前 debugTransport 和“没有 choices”分支可能把响应体放进 error。任务日志必须提取错误类型、阶段、HTTP 状态等诊断摘要，不能直接把这些错误的完整字符串写入。无可安全提取的内容时保留通用错误摘要；保持原有前端错误处理不变。普通文件系统错误可记录操作和路径。

## 6. token 统计口径

一轮定义为一次应用层 Chat.Completions.New 调用；轮次从 1 开始。耗时包围实际调用，包含 SDK 内部可能发生的重试耗时，不增加 HTTP 级重试日志，也不宣称能统计服务端未回传的消耗。

- 输入、输出、总量分别采用 Usage.PromptTokens、CompletionTokens、TotalTokens。
- 每轮返回后，在取消检查和 choices 检查之前记录已经收到的 usage，避免丢掉已返回的消耗。
- 使用 SDK JSON 字段有效性判断 usage 是否存在，不能凭数值为 0 判断缺失。当前依赖 openai-go/v3 v3.50.0 的 ChatCompletion.JSON.Usage 和 CompletionUsage.JSON 各字段提供 Valid 元数据。
- 某字段缺失或无效则显示“未知”。本轮 total 有效时累加；total 缺失时不推算该轮总量，累计只保留可确认 total，并将任务总量统计标为不完整。
- 输入或输出字段缺失但 total 有效时，可以继续准确累加已回传 total，同时标明分项未知。
- 请求失败没有 usage 时写本轮用量未知、任务统计不完整；发请求前就取消或预算拒绝，不虚构一次已执行请求。
- 有效的 0 是 0；未知不能显示为 0。后续轮次恢复返回 usage 后，之前产生的不完整标志不能自动清除。
- 上下文压缩可重置 agent.totalTokens，但不能重置累计 usedTokens 或日志累计值。

本功能不重写预算策略，也不变更 CleaningRecord.TokenUsage 字段或失败任务的数据库 token 持久化行为。日志保存失败/取消前已知消耗，即使失败记录的现有 TokenUsage 仍为 0。这里的“统计完整”仅表示应用调用获得了所需的用量信息，不代表服务商最终账单。

## 7. 历史记录联动删除

数据库模型负责选择和删除记录，文件操作由 cleaninghistory 协调 tasklog，避免模型依赖业务服务或使用 GORM 删除钩子做文件 IO。

将原 DeleteOldCleaningRecords 拆为两个持久化操作：

1. ListOldCleaningRecords(ctx, maxCount)：按 start_time DESC、id DESC 排序，跳过最新 maxCount 条，返回待删记录 ID 和 StartTime；保留 maxCount 非负校验。
2. DeleteCleaningRecordsByIDs(ctx, ids)：只删除传入 ID，在一个数据库事务内执行，空集合直接成功。

清理顺序：

```text
修复上次中断任务 → 读取保留数量 → 查询过期记录
    → 对每条记录按 StartTime 删除日志
        → 成功或不存在：加入可删除 ID 集合
        → 其他错误：应用日志报告，跳过该记录
    → 在事务中删除可删除 ID 集合
```

不能在最后重新按 Offset 查询删除目标，否则可能误删刚刚跳过的记录。某条日志失败也不能改删保留区的新记录来凑保留数量。文件清理部分失败不返回为启动失败；全部失败时保留全部候选，数据库删除为空操作。后续应用启动再次按保留策略自然重试，不添加后台重试任务。

若文件删除成功但数据库事务失败，事务回滚记录删除，已删除文件不会恢复。允许留下没有日志的记录，下次按“文件不存在即成功”继续。数据库事务失败仍向上返回。若关闭应用发生在两个阶段之间，同样处理。

旧版本记录没有日志也可正常删除，不回填历史日志。启动修复中断状态不重新打开旧日志或补造结束事件。当前启动清理在任务开始前执行，无需新增运行中删除协调；以后若新增手动记录删除入口，需复用该文件优先规则并处理活跃任务，属于后续功能。

## 8. 故障行为表

| 故障 | 任务/记录行为 | 日志行为 |
| --- | --- | --- |
| CleaningRecord 创建失败 | 启动失败，保持原逻辑 | 不创建文件 |
| exe 路径解析或目录创建失败 | 继续扫描和分析 | 应用日志报告，任务 Session 空操作 |
| 文件打开、写入或关闭失败 | 不改变业务结果 | 报告故障；写入失败后停用 Session |
| 扫描失败或取消 | 保持现有 ERROR/CANCELLED 行为 | 结束行，无虚构 LLM 用量 |
| LLM 失败/无 usage | 保持现有调用处理 | 保留已知 token，缺失项标未知 |
| 分析成功但结果落库失败 | 任务失败 | 记录失败及已知消耗 |
| 日志不存在 | 数据库记录可删除 | 不报文件删除失败 |
| 日志被占用、权限不足等 | 跳过该记录，其他记录继续 | 应用日志报告 |
| 数据库删除事务失败 | 本批数据库删除回滚 | 不恢复已删文件 |
| 强制退出 | 保持原有重启修复行为 | 可能缺少末尾日志，不补写 |

## 10. 验收与测试

使用临时目录、内存/临时 SQLite、fake Session/日志服务及本地模拟 LLM 响应，不依赖真实计费 API。路径和文件操作通过包内私有构造器提供测试替身，不增加生产构造器的测试参数。

| 验收项 | 验证要点 |
| --- | --- |
| 时间关联 | 已知 StartTime 生成预期文件名；创建和删除一致；已有文件不被截断 |
| 开始及实时可读 | 扫描前存在开始行；模拟下一轮阻塞时上一轮 token 已能从文件读取 |
| 正常结束 | 开始、扫描、配置、轮次、工具、结束顺序正确；结束仅一次并关闭文件 |
| 输出边界 | 测试提示词、回复、工具响应、API Key 哨兵不出现；完整工具参数出现 |
| 工具异常参数 | 非 JSON 参数仍可阅读且在 Invoke 前写入，不改变业务调用 |
| usage | 正常值、有效零值、缺失对象、缺失字段、请求失败；累计已知值及不完整标志正确 |
| 取消/失败 | 扫描失败、配置失败、LLM 失败、取消、结果落库失败均关闭文件并保留已知用量 |
| 原始错误 | 带响应体的错误不将响应体写进任务日志 |
| 压缩 | 状态变化被记录；累计 token 不被清零；不修改压缩行为 |
| IO 故障 | 打开/写入失败仍完成模拟分析；无重复故障刷屏 |
| 部分删除失败 | 三条候选中一条删文件失败，只事务删除其余两条；较新保留记录不受影响 |
| 缺失与回滚 | 旧记录无文件可删；数据库删除失败后文件已删、记录保留，再次清理成功 |
| 装配 | 日志路径失败不阻止服务发布；数据库失败仍遵循现有初始化失败规则 |

建议先运行 tasklog、analyzer、cleaner、cleaninghistory、data 及 service 的相关包测试，再运行 go test ./backend/... 检查接口变更影响。不需要真实 LLM 请求、前端测试或生成 Wails 绑定。
